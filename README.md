# point-money — TOKI

**ひらく、たまる。** PC・スマートフォン・タブレットで使える、日本語のポイント体験アプリです。

## 公開版の位置づけ

- アプリ: https://toki-rewards-kasai.hisa-0128-1996.chatgpt.site
- ソース: https://github.com/uni-tadayasu/point-money
- 初回スポンサー枠の販売条件レビュー: https://toki-rewards-kasai.hisa-0128-1996.chatgpt.site/sponsor
- 現在は本人向けの非公開体験版です。すべてのポイント・交換・スポンサー入金はテスト用で、金銭的価値はありません。
- 銀行振込・BTC・ETHの実送金、スポンサーへの実課金、本人確認サービスは未接続です。
- 本番送金を有効にする環境変数や隠しスイッチはありません。本番化には別途、資金・契約・適切な実装が必要です。

## 実装した機能

- ホームに、画面を開いてからの時間・一日の累計・当月の累計・ポイントを大型表示。スポンサー管理とメニューも同じ画面に配置。
- 日別・月別は日本時間で集計。月間の累計はカレンダー上の当月（毎月1日から）です。
- 画面表示中の時間計測、1分1テストポイント、1日180ポイント上限。
- サーバー時刻に基づく確定ポイント、残高、獲得履歴、日別記録。
- 15秒間隔の通信確認。非表示・通信断・長い通信間隔はまとめて遡及加算しません。
- 同一アカウントで1つの計測セッション、再送・並行更新・二重使用を考慮した更新。
- 100ポイントからの交換体験、取消・返却、同じ依頼の重複処理防止。
- スポンサー企画の保存、入金のシミュレーション、報酬・準備金・運営・成長予算への配分。
- 未確定のスポンサー下書き編集、掲載の停止・再開、画面内表示時間の参考レポート、提案文のコピー。
- KASAI SOLUTIONSを受取先とする初回スポンサー枠の販売準備画面（5,000円・30日間・1回払い）。決済リンクは未発行で、税区分・掲載先・販売者窓口を確認中。
- スポンサー資金のテスト台帳と、利用者のテストポイント台帳の分離。
- 30日間の報酬予算試算。入力値による計算であり、収入予測・利益保証ではありません。

未認証の開発プレビューでは、端末内だけの体験モードを利用できます。この残高をサーバー残高や本番残高へ取り込む機能はありません。認証エラー以外のサーバー障害・通信障害では、加算を停止します。

## 原資の設計

企業へ、ポイント還元のある商品・サービス紹介枠を直接販売する構成です。スポンサーが得るのは掲載枠と、定義した条件での掲載実績です。クリック、購買、人間の在席、成果を保証するものではありません。

掲載料の入金確認・控除・返金に備える保留を経た利用可能額を、初期の配分案では以下へ分けます。

| 用途 | 配分案 |
| --- | ---: |
| 利用者への報酬原資 | 50% |
| 準備金 | 20% |
| 運営予算 | 20% |
| 次のスポンサー獲得に使う成長予算 | 10% |

この配分は事業計画用の仮設定です。アプリでの入金処理はシミュレーションに限定され、実際の売上や預金にはなりません。詳しい考え方は [docs/business-model.md](docs/business-model.md) に記載しています。

実売の準備内容と残っている設定は [docs/sponsor-sales.md](docs/sponsor-sales.md) に記載しています。スポンサー管理画面上の販売条件のコピーでは、送信・契約・請求・決済は発生しません。

## 開発

Node.js 22.13.0以降を使用します。

```sh
npm ci
npm run dev
```

Vinext/React、Cloudflare Workers、Cloudflare D1、Drizzleを使用しています。アプリ本体はサーバー処理を必要とするため、GitHub Pagesだけではサーバー台帳は動きません。

```sh
npm run typecheck
npm test
npm run db:generate
npm run build
```

`db:generate` はスキーマを変更した場合にだけ実行します。生成済みSQLとDrizzleのメタデータはソースに含め、適用済みのマイグレーションは書き換えません。ローカルDBへの適用方法と実行環境の詳細は [docs/runtime.md](docs/runtime.md) を参照してください。

## 認証と運用境界

公開したサーバーAPIは、ホスティング基盤が確認した利用者IDで記録を分離します。認証ヘッダーを外部クライアントが偽造できる構成で、Workerを単独公開してはいけません。別のホスティングへ移す場合は、対応する認証境界を実装する必要があります。

ブラウザから送られる可視状態は、人間が見ていたことの証明ではありません。本番の換金運用には、複数アカウントの濫用対策、事業者との契約、資金照合、本人確認・審査、実送金後の照合を追加します。現状のデモをそのまま換金可能に変更することは想定していません。

本番化する際は、テスト台帳を流用せず、別台帳をゼロから開始します。秘密情報をソース、フロントエンド、GitHub、ホスティングマニフェストへ保存しないでください。
