# TOKI 初回スポンサー枠：販売準備

準備日：2026年11月25日（日本時間）

## 現在の状態

運営者から、**KASAI SOLUTIONS の本番Stripe口座を受取先として、5,000円・30日間の掲載枠の販売準備を進める承認**を得た。受取先の選択を再確認する必要はない。

アプリ内の `/sponsor` は、この商品の内容と販売条件をレビューするページ。スポンサー管理からも開ける。**本番Stripeに商品と税込5,000円の単発価格を登録済み。商品は販売保留中で、決済リンクは未発行。** 申込み、契約、支払い、返金、外部への営業送信は行っていない。

消費税を徴収し、Stripe Taxで税額を計算する方針も承認済み。税を徴収するかどうかを再確認する必要はない。実際の徴収開始は、対象地域での販売者の税務上の状態を確認してから設定する。

今回追加した販売準備データは、既存のスポンサー入金シミュレーションとは別。入金シミュレーションを行っても、この商品の購入や、実際の入金の確認にはならない。

## 提供開始と取消・返金の案

掲載文とリンクを先に確認し、公開範囲と開始日を合意した後に支払いを案内する。決済確認後7日以内に掲載を開始する。掲載期間は決済日からではなく、実際の開始日時から計算する。

掲載開始前の取消、または決済確認後7日以内に開始できない場合は、全額返金する。開始期限は運営の判断だけで延長しない。

開始後の取消では、未提供時間を30日間に対して按分し、1円未満を切り上げて返金する。運営都合の未掲載期間は、購入者が期間延長または未提供分の返金を選べる。返金総額は実際の支払額を超えない。

取消・未提供が確定してから7日以内に、運営が返金処理を行う。決済手段への着金時期は確約しない。返金の実行・照合を行う担当と窓口を用意する。**現在、自動返金機能はない。**

## 購入前に明示する媒体の状態

- 新規サービスであり、利用者数や広告実績は未確認。
- アプリを表示するとポイントが加算されるため、閲覧にはポイント獲得という目的が含まれる。人間の注視、商品への関心、クリックや購買を保証しない。
- 広告のクリックや商品購入をポイント付与の条件にしない。
- 現在のポイントはテスト用で、現金や暗号資産への交換は未提供。
- 現在のホスト先は運営者本人だけが閲覧できる確認版。一般の利用者が閲覧できる広告枠として、そのまま販売しない。
- 既存のアカウントごとの体験用協賛データは、本番の広告配信データではない。

## 入稿時に必要な情報

企業名・屋号、担当者名・連絡用メールアドレス、掲載タイトル・紹介文・リンク、希望開始日、掲載内容の使用権限、購入条件への同意を取得する。担当者の連絡先を広告カードへ公開しない。カード情報はStripeが取り扱い、独自フォームには入力させない。

入稿フォームはまだ接続していない。画面上の入力項目一覧は、申込みを受け付けるフォームではない。

## Stripeの登録内容と残っている設定

### 消費税

2026年11月25日、運営者から消費税の徴収とStripe Tax利用の指示を受けた。本番Stripeへ次の内容を登録し、返却された商品・価格を確認した。

| 設定 | 登録内容 |
| --- | --- |
| 商品 | `prod_Vh2qxT1ODf311I` |
| 単発価格 | `price_1UfekkL3ZjL9QUmfD1vfKS2p` |
| 通貨・金額 | `jpy` / `5000` |
| 税の表示方式 | `inclusive`。税を含む総額を5,000円に固定 |
| 商品の税区分 | `txcd_10701000` / Website Advertising（Web広告掲載） |
| 商品の販売状態 | `active: false`。購入受付は保留 |
| 継続課金 | なし |

税コードはStripe公式カタログで実在と説明を確認して選択した。アカウント全体の既定税コード、住所、既存商品は変更していない。

本番環境の請求プレビューで、登録した実際の価格、日本の顧客所在地、`automatic_tax.enabled: true` を指定して検証した。合計は5,000円で、返却された税の理由は `not_collecting`。**税の自動計算を指定したプレビューが成功しても、実際の徴収設定が完了したことにはならない。** このプレビューは購入者への請求・決済ではない。

販売者の実際の税務上の状態を確認する前に、所在地だけから税登録を追加しない。次に必要なのは、日本で現在課税事業者であるか（将来からなら適用開始日）の確認。Stripe Taxへの地域登録は、税務署への届出・登録を代行するものではない。

対象地域の設定後、登録済み価格を用いた請求プレビューを再実行し、税額だけでなく `taxability_reason` を確認する。購入リンクには `automatic_tax.enabled: true` を設定する。本番の有料Tax Calculations APIで代用しない。

### 掲載先と販売者窓口

購入者へ示す公開範囲、対象利用者が閲覧できる実際の掲載場所、本番の掲載データを整える。現在のサイトの共有範囲は変更していない。販売者情報、連絡窓口、取消・返金の窓口は未確定であり、連絡先を推測して埋めない。

### 購入リンクと支払確認

最初はStripe Payment Linksを使用する設計。1回払い・数量1、初回の完了セッション上限1を設定し、無制限の重複販売を避ける。支払い方法はStripeの動的表示に委ねる。

決済成功ページの表示を、支払い・掲載・原資計上の確定条件にしない。自動処理を実装する際は、外部から到達できる署名検証済みWebhookで `checkout.session.completed` と `checkout.session.async_payment_succeeded` を受信し、支払い状態を検証する。遅延支払いの失敗、返金、異議申立て、重複通知を扱い、注文と支払いを一意に照合する。本人限定のサイトにURLだけを追加してWebhookが通ると仮定しない。

現状はWebhook、入金照合、本番掲載、返金処理が未接続。購入リンクだけを発行して、これらも完成したとは扱わない。

## 受領金をポイント原資にする前に

商品登録・購入リンク作成・決済完了・Stripeでの利用可能残高・銀行入金・還元に利用可能な資金を、それぞれ区別する。未提供期間や返金義務に対応する額、税・手数料等を先に確保し、支出できる金額を確認してから配分する。

5,000円の掲載料を、そのまま5,000円のポイント原資として表示しない。現在の体験用ポイントを、入金に合わせて本番残高へ昇格させない。本番のポイント発行と実送金には独立した台帳・原資引当・送金照合を実装する。
